# Jiuwen-CodeHeal Swarm —— 系统架构与核心实现文档

---

## 1. 系统设计哲学与总体架构

Jiuwen-CodeHeal Swarm 的底层架构深度依托于两大国产开源框架：
1. **openJiuwen (`agent-core`)**：提供生产级智能体底层基座，包含计算图流转引擎（`Workflow`）、动态会话状态管理（`Session`）、组件注册中心（`Runner.resource_mgr`）与双模大模型驱动层；
2. **JiuwenSwarm (`jiuwenswarm`)**：提供高级多智能体协同机制，包含 **Leader-Teammate 团队协同范式**、**严格工具安全与文件权限白名单** 以及 **Skill 自演进知识记忆（Self-Evolution Memory）**。

### 1.1 系统分层架构

```text
+------------------------------------------------------------------------+
|                      Jiuwen-CodeHeal Swarm 系统架构                     |
+------------------------------------------------------------------------+
 [接入与交互层]
   - CLI 终端 (codeheal demo / heal / inspect / self-test)
   - Rich 格式化 Trace 树与彩色结果看板
   - Webhook / CI API 触发接口
 ------------------------------------------------------------------------
 [JiuwenSwarm 协同控制层]
   - SwarmLeader (意图识别 / 任务分解 / 调度器 / 轨迹归档)
   - Pydantic 全生命周期数据契约 (FaultSignature, ASTContext, PatchProposal, VerificationResult)
 ------------------------------------------------------------------------
 [openJiuwen Workflow 计算图编排层 (Swarmflow)]
   - Start 节点 -> [triage 节点] -> [inspect 节点] -> [verify 节点]
   - Conditional Branch (条件路由: 验证通过 -> evolve / 验证失败 -> ReAct 循环)
   - End 节点 (显式输入映射 ${result})
 ------------------------------------------------------------------------
 [领域工具集与引擎层 (Tool Components)]
   - Log Parser: 正则语法状态机，跨工具链报错解析
   - AST Inspector: Python AST 精准切片，依赖与调用链压缩
   - Sandbox Verifier: 白名单安全拦截，临时隔离沙箱，pytest 子进程驱动
   - Skill Evolver: 错误指纹计算，知识蒸馏，双模记忆持久化
   - Dual-Mode Engine: Live LLM 模式 <---> Deterministic Replay 模式
 ------------------------------------------------------------------------
 [基础设施与持久化存储]
   - skills/SKILL.md (JiuwenSwarm Skill 规范)
   - skills/learned_patterns.json (结构化模式经验库)
   - skills/ci_healing_memory.md (演化复盘日志)
   - ~/.jiuwenswarm/config/config.yaml / .env (配置中心)
+------------------------------------------------------------------------+
```

## 2. openJiuwen 计算图工作流编排 (`HealSwarmFlow`)

### 2.1 真实 API 绑定契约与最佳实践

在与 `openjiuwen.core.workflow` 对接时，本项目遵循了经终端内省验证的严格调用规范：
1. **工具注册顺序约束**：
   在 openJiuwen 中，`ToolComponent` 实例化时需根据 `tool_id` 寻址。因此，必须先调用 `Runner.resource_mgr.add_tool(fn)` 将 `@tool` 装饰的函数卡片注册入全局资源池，随后将生成的唯一 `card.id` 传递给 `ToolComponentConfig(tool_id=card.id)`。若顺序颠倒，框架将抛出 `[102002] tool component not bind a valid tool` 致命异常。
2. **节点间数据流驱动（Input Schemas）**：
   工作流节点之间通过显式表达式绑定数据依赖，例如：
   ```python
   wf.add_workflow_comp(
       "inspect", inspect_comp,
       inputs_schema={
           "file_path": "${triage.file_path}",
           "line_number": "${triage.line_number}",
           "repo_root": "${start.repo_root}",
       },
   )
   ```
3. **条件路由与闭环流转**：
   通过 `wf.add_conditional_connection("verify", router=_router)` 动态路由后继节点。若沙箱测试通过，流向 `evolve` 并汇聚至 `end_healed`；若未通过，则通过外层 Leader 控制器驱动 ReAct 循环，增量注入新报错日志。

### 2.2 双模驱动架构（Dual-Mode Engine）

系统通过 `src/jiuwen_codeheal/config.py` 实现自适应双模驱动：
- **Live LLM 模式**：
  读取环境变量或配置文件（`API_BASE`, `API_KEY`, `MODEL_PROVIDER`, `MODEL_NAME`），支持 DeepSeek-V3/R1、OpenAI GPT-4o、华为云盘古与 MaaS 接口，驱动 `openjiuwen.core.foundation.llm` 下的 `ModelClientConfig` 与 `WorkflowAgent` 进行深度补丁推导；
- **Deterministic Replay 模式**：
  当环境未注入任何 API Key 时（如 GitHub Actions CI 或离线评审环境），系统无缝切换至纯确定性 Replay 模式。由 `FixPolicy` 基于抽象语法树结构化模式进行安全生成，绝不因为缺 Key 崩溃。

## 3. JiuwenSwarm 多智能体协同机制

### 3.1 四大领域 Teammate 职责规范

| 智能体角色 | 对应模块与工具 | 核心职责 | 输入与输出契约 |
|:---|:---|:---|:---|
| **Log Triage Teammate** | `log_parser_tool.py` | 故障感知与跨工具链（pytest/flake8/mypy）日志解析 | In: CI 原始日志文本 $\to$ Out: `FaultSignature` |
| **Code Inspector Teammate** | `ast_inspector_tool.py` | 语法树精准切片、上下文压缩与补丁提案 | In: `FaultSignature` $\to$ Out: `ASTContext`, `PatchProposal` |
| **Sandbox Verifier Teammate** | `sandbox_verifier_tool.py` | 白名单安全拦截、隔离工作区补丁应用与 pytest 验证 | In: `PatchProposal` $\to$ Out: `VerificationResult` |
| **Skill Evolver Teammate** | `skill_evolver_tool.py` | 错误指纹沉淀、模式蒸馏与自演进知识库维护 | In: `HealingTrajectory` $\to$ Out: `LearnedPattern` |

### 3.2 自纠错闭环（ReAct Loop）实现逻辑

当待修复仓库中存在多个关联或复合 Bug 时（例如 `examples/buggy_repo_demo` 同时存在越界 Bug 与除零 Bug）：
1. **第一轮迭代**：
   - Log Triage 解析发现用例在 `calc.py:22: in find_max` 触发 `IndexError`；
   - Code Inspector 识别 `seq[i + 1]` 越界访问，提议修改为 `seq[i]`；
   - Sandbox Verifier 在沙箱内应用补丁 1 并运行测试；
   - 测试结果：5 用例通过，1 用例失败（`test_average_empty` 仍报 `ZeroDivisionError`）；
   - 判定尚未全绿，保留已成功的补丁 1；
2. **第二轮迭代**：
   - 捕获沙箱第一轮的测试输出，提取新报错 `calc.py:32: in average`；
   - Code Inspector 分析 `average` 函数语法树，提议插入 `if not values: return 0.0` 空守卫；
   - Sandbox Verifier 在已包含补丁 1 的沙箱基础上增量应用补丁 2 并再次执行 pytest；
   - 测试结果：6/6 用例全部通过（100% All Green）；
3. **收敛结算**：
   - 触发 Phase 4 自演进沉淀，生成合并后的双 Bug 修复 Unified Diff。

## 4. AST 语法精准切片与上下文压缩技术

传统基于大模型的代码修复方案往往将整个文件甚至全仓库代码塞入上下文，引发 Token 浪费与幻觉干扰。
本项目在 `ast_inspector_tool.py` 中实现了 **AST 精准切片与上下文压缩机制**：

1. **内层作用域查找（Enclosing Node Detection）**：
   通过 `ast.walk(tree)` 遍历抽象语法树，精准锁定包含故障行号的最深层 `ast.FunctionDef` 或 `ast.ClassDef` 节点；
2. **函数上下文提取**：
   通过 `ast.get_source_segment` 提取故障函数的完整代码片段，剥离无关业务函数；
3. **依赖与导入提取**：
   仅提取模块顶层的 `Import` 与 `ImportFrom` 声明，供补丁环境理解类型注解与依赖库；
4. **调用链追踪（Call Chain Extraction）**：
   静态分析函数体内部调用的系统内置函数与自定义子函数（如 `sum`, `len`），形成形如 `sum -> len` 的精简调用拓扑；
5. **Token 预算裁剪（Budget Clamp）**：
   通过 `compress_context` 函数对最终组装的上下文实施长度截断（默认 6000 字符以内），确保输入始终紧凑、高信噪比。

## 5. 安全沙箱与白名单拦截设计

为杜绝自动化脚本对开发机或宿主机环境造成意外破坏，`sandbox_verifier_tool.py` 设计了三重防护机制：

### 5.1 路径穿越白名单防护 (`SecurityError`)
```python
def resolve(self, rel_path: str) -> Path:
    if self.root is None:
        raise SecurityError("sandbox is not active")
    candidate = (self.root / rel_path).resolve()
    root_resolved = self.root.resolve()
    if os.path.commonpath([str(candidate), str(root_resolved)]) != str(root_resolved):
        raise SecurityError(
            f"path '{rel_path}' escapes the sandbox whitelist "
            f"(resolved to '{candidate}', root '{root_resolved}')"
        )
    return candidate
```
任何以 `../` 企图跳出沙箱根目录，或直接引用系统盘敏感路径的候选补丁，均会在解析阶段被即刻拦截。

### 5.2 原子化替换与崩溃回滚
在应用补丁时，系统备份目标文件内存镜像。若 Unified Diff 的上下文在目标文件中无法精准匹配，系统放弃应用并执行原子回滚，并向 Leader 汇报 `ok=False`，引导规划智能体调整策略。

### 5.3 隔离执行与环境注入
沙箱目录在临时文件系统（`tempfile.mkdtemp`）中生成，通过子进程执行 pytest 时显式注入：
```python
env = os.environ.copy()
env["PYTHONPATH"] = str(sandbox.root) + os.pathsep + env.get("PYTHONPATH", "")
```
确保 Python 解释器优先加载沙箱内被修复的模块，杜绝全局安装包干扰。

## 6. Skill 自演进架构与知识库维护

系统的第四阶段对齐了 JiuwenSwarm 的 **Skill Self-Evolution** 理念：

### 6.1 错误指纹计算与幂等去重
系统提取四元组：
$$\text{Fingerprint} = \text{SHA1}\Big(\text{FaultType} \mid \text{RelFilePath} \mid \text{FunctionName} \mid \text{ExceptionType}\Big)[:16]$$
保证同一类型的缺陷具有跨环境唯一确定的指纹标识。

### 6.2 知识持久化机制
每次成功自愈后，`skill_evolver_tool` 自动执行持久化：
1. **`skills/learned_patterns.json`**：
   存储包含 `fingerprint`、`root_cause`、`strategy`、`fix_template`、`occurrences`、`success_count` 的结构化知识库；
2. **`skills/ci_healing_memory.md`**：
   追加人类可读的自愈复盘日志，详细记录每次自愈的发生时间、耗时、修复方案与 Trace 步骤。

通过该机制，当后续工程再次遇到类似越界或空指针问题时，系统可优先检索高置信度经验库，实现毫秒级快速匹配与零幻觉自愈。
